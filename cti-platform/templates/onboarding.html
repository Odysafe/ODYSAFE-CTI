Cross-linking

How data connects

IOCs live in SQLite. CTI Memory holds searchable context. Modules share stable keys so you can reuse values without retyping.

Authoritative IOC store

  1. SQLite: IOCs, sources, tags, MITRE links (ioc_ttp_links)
  2. CTI Memory: indexed text with keys like odysafe:ioc:{id}
  3. Intelligence Workspace: SQLite-backed JSON save, with browser draft recovery

Reuse in reports

  1. IOC detail → Use in Intelligence Workspace
  2. IOC list / MITRE → Add Memory note (attach context)
  3. Intelligence Workspace → import indicators (TLP, notes, MITRE techniques)
  4. Save workspace → summary indexed in CTI Memory

Not automatic

  1. Quick Export → no database, no Memory
  2. STIX Graph → separate from IOC database

Offline Data

Manual data placement

Use these local paths when the platform cannot download required datasets from the internet. Paths are relative to the ODYSAFE-CTI repository root unless stated otherwise.

MITRE ATT&CK Enterprise

  1. Expected file: docs/enterprise-attack.json
  2. Place the official Enterprise ATT&CK STIX JSON bundle at that exact path.
  3. Used by: /cti-resources/mitre-attack, ATT&CK technique search, Navigator export, and profile TTP selection.

DeepDarkCTI repository

  1. Expected folder: cti-platform/modules/deepdarkCTI-main/
  2. The folder should contain the cloned fastfire/deepdarkCTI repository, including its .git folder when possible.
  3. Cache/favorites live in: cti-platform/modules/cache/

Ransomware Tool Matrix repository

  1. Expected folder: cti-platform/modules/Ransomware-Tool-Matrix-main/
  2. The folder should contain the cloned BushidoUK/Ransomware-Tool-Matrix repository, including its .git folder when possible.
  3. Cache/favorites live in: cti-platform/modules/cache/

Data-Shield IPv4 Blocklist

  1. Expected file: cti-platform/modules/data_shield/prod_data-shield_ipv4_blocklist.txt
  2. Use the plain text IPv4 blocklist file. Keep one IP per line as provided by the source.
  3. Cache file: cti-platform/modules/cache/data_shield_cache.json

Runtime data folders

  1. Uploaded source files: cti-platform/uploads/
  2. Generated outputs: cti-platform/outputs/
  3. IOC exports: cti-platform/outputs/iocs/
  4. Report exports: cti-platform/outputs/reports/
  5. STIX exports/imported graph files: cti-platform/outputs/stix/
  6. SQLite database: cti-platform/database/cti_platform.db
  7. CTI Memory store: cti-platform/data/zettelforge/
  8. SSL files: cti-platform/ssl/

Custom HTTPS certificate

  1. Certificate path: cti-platform/ssl/cert.pem
  2. Private key path: cti-platform/ssl/key.pem
  3. Replace both files with your own PEM certificate and key, then restart ODYSAFE.
  4. Keep the private key readable only by the ODYSAFE runtime user when possible.

Important offline notes

  1. Do not place downloaded datasets inside outputs/ unless the module explicitly expects them there.
  2. Restart ODYSAFE after manually placing MITRE, repository, or blocklist files.
  3. Use Settings → Health Check to confirm SQLite, folders, storage, MITRE data, and SSL readiness.

Connections

How it fits together

Most cases follow a simple path. Pick the scenario that matches yours.

Default workflow

Extraction → IOCs → Memory → Analysis → Intelligence Workspace → Export

IOC triage only

  1. Extraction → import sources
  2. Sources → review exact duplicate warnings or overlap recurrence when needed
  3. IOCs → filter, tag, validate
  4. Export → download blocklists

Full CTI case

  1. Extraction → import reports (Memory: source ref)
  2. IOCs → TP/FP, TLP, notes, MITRE links; click value for Memory note
  3. Memory → workspace search, titled notes on IOCs/TTPs
  4. Analysis → use MITRE, Navigator export, actor ATT&CK snapshots, or Profiles & Clusters as needed
  5. Intelligence Workspace → import indicators, use selected IOC details, and check Sigma ATT&CK mapping when detection rules are included
  6. Export → scoped IOC lists

Analytic vocabulary

Semantic contract

These terms keep the UI, JSON, Excel exports, and analyst interpretation aligned.

Knowledge states

  1. KNOWN: established and entered information.
  2. UNKNOWN: relevant information cannot currently be determined.
  3. NOT_ASSESSED: not yet searched for or assessed.
  4. NOT_APPLICABLE: does not make sense in the current context.

Analytic status

  1. OBSERVED: direct evidence is available to the analyst or organization.
  2. REPORTED: an identified source reports it; external observation remains reported in ODYSAFE.
  3. INFERRED: analyst conclusion derived from evidence and rationale.
  4. UNKNOWN: relevant question with insufficient information.

Interpretation guardrails

  1. Indicator match does not equal compromise.
  2. NO_HIT does not prove absence of activity.
  3. ATT&CK mapping does not prove internal observation or detection coverage.
  4. External attribution does not become ODYSAFE attribution unless explicitly assessed.
  5. CVSS severity does not determine internal priority without exposure and relevance context.

Operational terms

  1. Publication Readiness: required product information is present; it is not correctness or confidence.
  2. Block Candidate: eligible for blocking review, not automatic approval.
  3. False Positive Risk: expected risk of disrupting legitimate activity if used alone.
  4. Discriminative Value: how strongly an artifact distinguishes the studied activity.
  5. Artifact Context: whether an artifact is attacker-controlled, victim-internal, benign, or unknown.
  6. Expected Outcome: intended result, not proof that the result occurred.
